# 流程文档与标准操作流程（SOP）

SOP 说明流程边界、步骤、角色及关键条件；逐次操作细节用 `bo-runbook`。本技能将原业务逐项整理，不以完整制度模板补造规则。

## 成稿

短稿优先用“步骤｜角色｜动作及条件”一张表；将已给检查点和人工确认放进对应步骤。只在表后补用户要求且表中尚未表达的异常、人工升级或待确认项。不要另写重复职责表、检查清单和确认清单。

原话里的分派者、承办者、检查者分别保留。姓名、时限和特殊权限未给，仅该字段待确认，就地短注，不要另写完整待确认清单。审批触发条件与被批准的动作一起保留，不移成无关动作的前置条件。原话“采购经理审批未完成”已经给了审批角色；即使审批位置或权限范围未给，也不能把审批者改为未知。“有时审批延迟”只作为已知现象或异常，不因此新增独立审批步骤。

已知审批延迟却未说明它对应哪个步骤时，写明现象并将对应环节留待确认；不得把延迟并入最近的核对、分派等已知步骤。已知某岗位负责分派时，不再把“谁分派”列为未知；仅将改派、唯一权限或额外授权范围等未给部分单独待确认。标题中的“关闭”“完成”等终点也必须与原材料和正文一致。

建议的触发条件与理由也按同一标准核验。“建议对因审批延迟而未分派的事项……”仍断言了未经证实的因果，不能使用；可建议先确认审批环节，再为该环节约定提醒与升级方式。表中已写的检查点、异常和待确认项不再另起章节重复。

例（虚构）：“店员登记预约，店长确认档期后指定服务人员，服务人员接待。”表中写店长指定、服务人员接待。未知的是具体人员或确认时限，不能再问是谁指定人员；预约调整流程未提供，也不能自行写店员负责调整。

异常已有处置照录；未知处置写“处置/接收角色待确认”。用户需要改进时另列必要的“建议补充”，保持待采纳身份；不要为等待确认自行设暂停、登记或越级审批制度。

例（虚构）：“核对借用物，带出馆外须馆长批准。”带出馆外前需批准，馆内使用不因此扩大为须批准；核对不是必须等批准后才能做。

完整制度才增加适用范围、输入输出、流程图、版本或 RACI。起草不代表已发布或执行，行动遵循角色文件授权约定。

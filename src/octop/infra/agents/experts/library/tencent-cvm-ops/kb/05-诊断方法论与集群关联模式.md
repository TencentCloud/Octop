# 诊断方法论与集群关联模式

## 一、单机诊断：四层推进

| 层 | 看什么 | 判读要点 | 何时下潜 |
|---|---|---|---|
| L0 对象 | 实例状态、规格、可用区、公网 IP、到期时间 | STOPPED 就不查负载；规格是判读负载的分母 | 状态异常先处理状态 |
| L1 云监控 | CPU/内存/磁盘/网络/负载的**时间曲线** | 找突变点，不只看当前值 | 曲线能解释症状就停 |
| L2 OS 快照 | `cvm-patrol.sh` 一次采集 | load/free/df/ss/进程/内核错误 | 需要进程级、文件级证据 |
| L3 假设验证 | 针对具体假设再跑 1–2 条定向命令 | 一条命令对应一个假设 | 验证完即出结论 |

判定顺序：**先看变化再看绝对值**。`02:00 起线性上涨 56 小时` 比 `当前 86%` 有价值得多。

## 二、常见症状 → 首选假设

| 症状 | 首选假设 | 第一步验证 |
|---|---|---|
| CPU 高但业务量未变 | 异常进程 / 软中断 / 容器 throttle | `top -bn1`、`vmstat 1 3` |
| 负载高但 CPU 空闲 | IO 等待或 D 状态进程 | 看 `wa`、`ps -eo stat,comm \| grep '^D'` |
| 内存持续涨、重启归零 | 应用内存泄漏 | 对比 RSS 曲线与重启时间 |
| 磁盘满但删了文件没用 | 删除未释放（句柄） | `df` − `du` 差值 > 10G → `lsof +L1` |
| 时通时不通 | 连接数打满 / conntrack / 安全组 | `ss -s`、`nf_conntrack_count` |
| 服务反复重启 | 启动即崩（配置/依赖/端口） | `journalctl -u <svc> -n 80` |
| 多台同时变慢 | 共享依赖或批量变更 | 命中下方关联模式 |

## 三、集群关联：5 种模式

| 模式 | 触发条件 | 首选假设 | 验证重点 |
|---|---|---|---|
| 1 内存级联 | ≥3 台 mem > 80% | 共享 DB/Cache 压力；同一应用泄漏 | 各节点 top 内存进程名是否相同 |
| 2 负载不均衡 | max−min(load/ncpu) > 0.5 | CLB 后端健康检查异常、连接倾斜 | 各节点 ESTABLISHED 连接数分布 |
| 3 磁盘同步增长 | ≥2 台根盘 > 75% | 同一脚本写同一路径、日志未轮转 | 各节点 top 目录名称是否一致 |
| 4 网络退化 | ≥2 台 ss 异常或 DNS 超时 | 安全组/ACL、DNS、对端限流 | 同 VPC 互通性、解析耗时 |
| 5 服务级联 | 同一 systemd 服务 ≥2 台 failed | 配置批量下发、依赖服务挂 | 各节点该 unit 的失败时间与报错 |

**判定纪律：**
- 只有 1 台异常 → 单机问题，按四层诊断走，不要套模式
- 2 台异常但指标无关 → 分别处理，不要强行找共性
- 模式判定必须给证据（进程名、连接数、目录名、时间）

## 四、节点健康度评分（100 分制扣分）

| 条件 | 扣分 |
|---|---|
| load / ncpu > 2.0 | -25 |
| mem_pct > 90% | -20 |
| disk_root_pct > 90% | -25 |
| sshd 非 active | -40 |
| 云端 CPU 均值 > 90% | -15 |

分级：≥85 正常 / 60–84 关注 / <60 异常。

使用约束：
1. 只允许在**同角色、同规格**节点间比较排名
2. 缺项（TAT 离线）时不扣分但需标注"缺 OS 证据"
3. 评分是为了排序优先级，不能替代根因分析

## 五、结论写法

```
结论   一句话 + 关键数值
依据   - 时间线：什么时候开始、变化幅度
       - 直接证据：命令输出/指标值
       - 排除项：排除了什么、凭什么排除
建议   1. 动作（可执行、含具体路径/服务名）
       2. 影响与回滚
```

禁止"疑似""可能""建议进一步排查"这类无信息量的收尾。

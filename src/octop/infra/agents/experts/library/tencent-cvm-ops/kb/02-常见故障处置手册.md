# CVM 常见故障处置手册

每个故障按「取证 → 判定 → 处置 → 验证」四步。处置动作必须遵守变更门控（见《变更门控与回滚规范》）。

## 1. 磁盘满 / 删了不释放

取证：
```bash
df -h / ; df -i /
du -xhd1 / | sort -h | tail -6
lsof +L1 | grep -i deleted
```

判定：

| 现象 | 结论 |
|---|---|
| df 已用 ≈ du 合计（差 < 5%） | 文件确实多 |
| df 已用 − du 合计 > 10G | 存在被删除但仍被进程持有的文件 |
| df -h 不高但 df -i 高 | 大量小文件耗尽 inode |

处置：
- 文件多：优先清 `/var/log`（先 logrotate 归档，再删旧归档）；`/var/cache`、`~/.cache` 可清；业务数据不得直接删
- 删除未释放：对持有进程做 `systemctl reload <svc>` 或重启该服务（不是整机）；确认后可 `kill -HUP`
- inode 满：定位为目录后（`find / -xdev -type d -size +100M` 之类）按业务归属处理

验证：`df -h` 已用下降；`lsof +L1` 不再列出该文件；24 小时后复查增长速率。

## 2. 内存持续增长 / 接近打满

取证：
```bash
free -m
ps -eo pid,ppid,pmem,rss,comm --sort=-rss | head -10
grep -E 'MemAvailable|Slab|SReclaimable' /proc/meminfo
dmesg -T | grep -i 'killed process'
```

判定：
- `available` 仍 > 15% 且 buff/cache 占大头 → 正常，缓存可回收
- 单进程 RSS 单调增长、重启后归零 → 进程内存泄漏
- Slab/SReclaimable 很大 → 内核对象堆积（dentry/inode）
- 出现 `killed process` → 已发生 OOM，属异常

处置：
- 泄漏进程：重启该服务（🟡），观察 RSS 是否回落；回落即确认，建议上报研发并临时加内存上限
- Slab 堆积：`echo 2 > /proc/sys/vm/drop_caches`（🟡，只回收可回收部分），持续堆积用 `slabtop -o | head` 定位
- 容量不足：给"当前峰值 / 建议规格"，改配需停机（🔴）

验证：`free -m` 的 available 回升；泄漏场景观察 10 分钟 RSS 曲线是否持平。

## 3. CPU 高 / 负载高

先分清 CPU 忙还是 IO 等：
```bash
cat /proc/loadavg
top -bn1 | head -15
vmstat 1 3          # 看 r（可运行队列）与 wa（IO 等待）
mpstat -P ALL 1 2   # 是否有单核打满
```

判定：
- us+sy 高、r 大 → CPU 真忙，找 top 进程
- wa 高、r 不大 → IO 慢，查磁盘/网络存储
- sy 异常高（>30%）→ 系统调用/软中断，查 `ss -s`、网卡中断
- load 高但 CPU 空闲 → 大量 D 状态进程（`ps -eo stat,comm | grep '^D'`）

处置：
- 单进程打满（🟡）：确认是否业务预期（压测/批量任务）；非预期则限流或经确认重启该进程
- 软中断高：定位网卡/中断，多队列绑定建议交研发
- 规格不足（🔴）：给建议规格，改配需停机

验证：`vmstat 1 3` 的 r 回落、top 首进程 CPU 下降。load 有 5–15 分钟滞后，不能立刻判定。

## 4. 网络异常

分层排查，不要一上来改安全组：
```bash
ss -s
ss -tn state established | wc -l
ip -s link | grep -A1 errors
cat /proc/sys/net/netfilter/nf_conntrack_count 2>/dev/null
getent hosts <域名>
```

| 层 | 现象 | 结论 |
|---|---|---|
| DNS | getent 失败 | resolv.conf / 内网 DNS |
| 监听 | ss -tlnp 无端口 | 服务问题，不是网络 |
| 安全组 | 规则缺失/方向反 | 补规则（🔴，需列端口/源IP/方向） |
| 连接数 | TIME_WAIT 暴涨 | 短连接风暴，建议连接池/keepalive |
| conntrack | 接近上限 | 调 nf_conntrack_max（🟡） |

验证：同 VPC 另一台机器 `telnet <ip> <port>` 或 `curl -sv`；复采 `ss -s`。

## 5. 服务异常（failed / 反复重启）

```bash
systemctl --failed
systemctl status <unit> --no-pager -l
journalctl -u <unit> -n 80 --no-pager
systemctl show <unit> -p NRestarts
```

| 现象 | 结论 |
|---|---|
| NRestarts 持续增长 | 启动即崩，看日志首行 |
| status=203/EXEC | 可执行文件/路径错误 |
| status=226/NAMESPACE | 权限/命名空间问题 |
| OOM killed | 转内存故障处置 |

处置（🟡）：备份当前配置 → 回滚到上一可用版本 → `daemon-reload && restart`。端口被占先 `ss -tlnp | grep :<port>` 定位占用者。

验证：`systemctl is-active` = active，NRestarts 不再增长，业务探针通过。

## 6. 时间同步 / DNS 配置漂移

```bash
timedatectl
chronyc tracking 2>/dev/null || ntpq -p 2>/dev/null
cat /etc/resolv.conf
```

时间漂移 > 60 秒会导致证书校验失败、鉴权失败、日志时间错乱，也会让"监控时间对不上"。

处置（🟡）：`systemctl restart chronyd` 或重新指向内网 NTP；改完立即验证 `NTPSynchronized: yes`。

## 7. 实例状态异常

| 状态 | 含义 | 处置 |
|---|---|---|
| STOPPED | 已关机 | 需用户确认后 Start（🔴） |
| REBOOTING / PENDING | 中间态 | 等 3–5 分钟再查，不要连续操作 |
| RUNNING 但连不上 | 网络/服务/密钥 | 按网络与服务故障排查；必要时 VNC 看系统层 |

验证：`DescribeInstances` 状态回到 RUNNING，且 TAT 能拿到 `uptime` 输出。

2. 报告写明：改了什么 / 依据 / 当前状态 / 遗留风险

### #6 §4.5 ask_user_question 方案 —— 机制成立，三处需补

- **`allowed_decisions=["respond"]` 不可配**：`agent.py:1377-1383` `_resolve_interrupt_on()` 里 `interrupt_on[ASK_USER_TOOL_NAME] = {"allowed_decisions": ["respond"], ...}` 是**硬编码**。可配的只有 `ask_user_enabled`（开/关，`config/__init__.py:670`）与 `tools_disabled`（禁工具）。v2.0 步骤 2 写「`allowed_decisions=["respond"]`」是**描述现状**（准确），但若理解为「可配」则错。无需改值，但措辞应写明「沿用硬编码 respond，不新增 approve/edit」。
- **步骤 4「回复 → 落库」机制未指明**：`ask_user_question` 恢复后，respond 文本回到**agent 的工具结果**，agent 继续跑。`requirement_nodes.status/confirmed_by` 的写入要么靠一个 agent 可调用的落库工具，要么靠 resume 侧 service hook。v2.0 只写「回复 → 写 requirement_nodes.status」没说清由谁写、怎么写，这是 5 步里唯一的实质缺口。
- **「群里拍板」与 §2.2/§2.3 存在张力**：`format_ask_card`/`collect_ask_reply`（`hitl/format.py:129`、`hitl/coordinator.py:230`）是 **IM 通道**的卡片/收集；Dashboard 走的是 `/agents/{agent_id}/chat/hitl/resume`（`chat/routes.py:185`）。但 §2.2 明确「IM 回流不做、讨论只 Dashboard」，§4.5 收益却写「Owner 在飞书/企微群里直接拍板」。M1 若只 Dashboard，该收益不成立，需澄清 Owner 拍板的实际通道。

**可行性总体结论**：机制存在且语义契合（工具 docstring 明写「real implementation is the human」，且示例含「confirming a destructive migration」这类决策叉）；**基本可行**，但需补「落库机制」与「拍板通道」两处，且注意它**必须由一次 agent turn 触发**（无法由 service 直接发一张审批卡而不启动 turn）——这落在 v2.0 自己标注的「触发条件由 T3.3 明确」内，属合理延后但属未闭环。

### #8 T2.5 派单调用链 —— `create_thread` 对，`run_in_session` 命名错

- `ThreadRegistry.create_thread(*, agent_id, user_id, channel_type, session_key, title=None, last_active=0, thread_id=None) -> str`（`gateway/threads.py:427`）：存在且「不重绑会话」，与 T2.5 步骤①吻合。✅
- **「发消息走 gateway.run_in_session()」不准**：`run_in_session(agent_id, session_key, operation)`（`gateway/gateway.py:400`）是**会话锁包装器**，参数是 `Callable`，不是「发消息」API。真正让 assignee agent **开工**的路径是 cron 的 `_deliver_agent`（`infra/cron/delivery.py:132-173`）：`build_harness_request(...)` → `agent_manager.stream(agent_id, request)` → 最后 `push_session_text`。只 `create_thread` + `push_session_text` 只会插一行 thread + 推一条文本气泡，**agent 不会跑**。
- **team 触发 room 的前提**：room 由 host 在自己的 turn 里调 `ask_agent`（async）触发（`infra/agents/teams/team_manager.py:570-580` `_is_group_dispatch`）。因此发给 team host 也必须走「启动 host turn」（`agent_manager.stream`），不是推文本。v2.0 的「同一路径发给 team host；host 的 ask_agent(async) 自动触发 room」方向对，但「同一路径」应明确是 **stream 路径**而非 run_in_session/推文本。

**正确写法建议**：T2.5 步骤③改为「用 `build_harness_request` + `agent_manager.stream(assignee_id, request)`（参照 `CronDeliveryService._deliver_agent`），最后 `push_session_text` 回显」；`run_in_session` 仅作外层锁。

### #10 T2.1 项目 KB 创建 —— 内部调用可行，回滚需补偿

- KB 创建入口是领域服务 `KnowledgeService.create_base(...)`（`infra/knowledge/service.py:95`），非 HTTP handler，projects/service 可直接经 `server.services` 调用。✅
- 但 `create_base` 内部会 `assert_knowledge_usable`（KB 功能未启用即失败）并受 `MAX_BASES_PER_OWNER` / `max_documents` 上限约束（`service.py:106-113`）——这些都会抛错，是「失败」的常见来源。
- **「整体回滚」不是天然成立的**：现有 repo 模式是「每方法各自 `self._db.connect()/transaction()`」，没有跨 repo 的共享事务。projects INSERT、members INSERT、KB create、kb_id UPDATE 四步跨 `projects`/`knowledge` 两个 repo，做不到单事务原子回滚。正确做法是 **try/except + 补偿删除**（失败时删掉刚建的 KB 行与 projects 行），而非字面「整体回滚」。另外「立项人必须同时有 KB 权限」只覆盖权限轴，未覆盖「KB 功能未启用 / 超上限」场景，应一并归入 `PROJECT_KB_BIND_FAILED` 的错误面。

## 四、§4.5 ask_user_question 方案可行性专项结论

**结论：基本可行（语义正确、机制现成），但三处未闭环，不能直接照抄落地。**

1. 注册与拦截：`octop_harness/builtin/tools/ask_user.py:98` `@tool`；`agent.py:1347` 挂载、`agent.py:1377-1383` 加 `interrupt_on`（HumanInTheLoopMiddleware 在工具执行前拦截）。✅
2. 语义契合：工具 docstring 明确定位「decision fork / real implementation is the human」，与「Owner 确认需求节点草案」一致，优于 HITL 的工具审批语义。✅
3. 未闭环①：`allowed_decisions=["respond"]` 硬编码，不可配（但 v2.0 无需改值，措辞应澄清）。
4. 未闭环②：步骤 4「回复 → 落库」缺机制（需 agent 落库工具或 resume 侧 hook）。
5. 未闭环③：必须由一次 agent turn 触发；「群里拍板」依赖 IM 通道，与 §2.2「IM 不做」冲突，M1 实际拍板通道应是 Dashboard。

## 四、PG 专项结论

1. **「控制面已在 PG、项目记忆复用同一 DSN」——成立（已核实）**。`memory_backend.py:32-39`：控制面为 PostgreSQL 且 memory.backend 未配置时，默认返回 `{"type":"postgres","dsn": octop_config.database.postgresql_conninfo()}`，即复用控制面 DSN。注意：现默认 namespace 是 `agent_{agent_id}`（`open_memory_kwargs` 写死 `ns = f"agent_{agent_id}"`，memory_backend.py:76），`project_{id}` namespace 是 M2 新门面自行构造，**不会**走 `open_memory_kwargs`，与计划「ProjectMemoryStore 门面」设计一致，无矛盾。
2. **octop_memory 确为独立 schema**：`octop-memory/.../postgres.py:44` `SHARED_SCHEMA = "octop_memory"`，固定表集 + `namespace` 列隔离，非「每 namespace 一套表」。计划的「零 DDL、namespace 隔离」描述准确。
3. **连接预算**：控制面池 `max_size=8`（pool.py:154 已核实）；每个 `Memory` 实例 = 1 条裸连接（postgres.py:119 `self._conn = self._connect()`，无池，已核实）。M1 不碰记忆 → 预算维持 `8 + N_agents`（既有），**M1 成立**。M2 新增 `N_projects` 条裸连接；计划 R4 已登记「泄漏」且 S3 硬约束 #1/#2 有「硬上限 + 显式 close」。**缺口**：未把可行性分析里的「连接泄漏回归测试（连续建/销 100 项目后 `pg_stat_activity` 不增长）」和「`max_connections` 调多大 / 超限是淘汰还是拒绝」写进 M2 任务卡。
4. **备份覆盖 octop_memory schema——成立**：`system_archive.py:259-264` PG 分支调 `dump_postgres(...)`，`pg_dump.py:31` 命令为 `pg_dump -Fc -f dest --dbname conninfo`（**无 `-n`**）→ 整库导出，`octop_memory` schema 自动包含。D3「备份白拿」成立。
5. **pg_dump 缺失前置——已登记为 R9**（「部署镜像需含 PG 客户端工具」），但未纳入 §6 开工前自检（见 §3.2）。
6. **补充部署前置（计划漏）**：octop-memory PG 后端首次打开会 `CREATE SCHEMA IF NOT EXISTS octop_memory`（postgres.py:282）→ **控制面 PG 账号需有数据库内 CREATE SCHEMA 权限**；且 FTS 复合索引可选依赖 `btree_gin` 扩展（postgres.py:628-670），缺失时退化为 namespace-agnostic FTS（召回性能劣化）。两者均未在计划登记 PG 版本/扩展要求。

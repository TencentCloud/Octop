## 二、不成立 / 部分成立的断言明细

### #2 「7 处 assert v == 17」—— 部分成立（**计划最需要修正的硬伤之一**）

`tests/unit/db/test_db_pool.py` 实际有 7 处版本断言，但只有 2 处是字面 `assert v == 17`：

- `assert v == 17`：`test_db_pool.py:102`、`test_db_pool.py:184`
- `assert version == 17`：`test_db_pool.py:321, 346, 381, 464, 670`

计划 T1.2 的验收 `grep -c 'assert v == 18'` 期望 7，实际只会得到 2；`grep -c 'assert version == 18'` 才命中另外 5 处。**验收命令写错**。

更严重的是：**版本 17 断言散布在 7 个文件共 14 处**，计划只字未提其余 6 个文件：

| 文件 | 行号 |
|---|---|
| tests/unit/db/test_skill_package_icons.py | 94, 113 |
| tests/unit/db/test_skill_packages_repo.py | 31 |
| tests/unit/db/test_repo_knowledge.py | 53 |
| tests/unit/db/test_published_experts_repo.py | 30 |
| tests/unit/db/test_clip_thread_title.py | 85 |
| tests/unit/db/test_agent_profile_columns.py | 122 |

**正确做法建议**：迁移号断言应全局搜索 `assert (v|version) == 17`（14 处、7 文件），全部改为 18；§7 检测脚本的 `sed` 也应同步处理这两种拼写与多文件，而不是只改 `test_db_pool.py`。

### #3 附录 A DDL 与 §7 资源表约定 —— 部分成立

主体符合（整数 `id` PK + 字符串 `{entity}_id` UNIQUE + 子表 FK 字符串 id：`project_members.project_id REFERENCES projects(project_id)` 等）。两处瑕疵：

1. **多态成员列混用类型**：`project_members.subject_id TEXT`、`project_room_members.subject_id TEXT`、`project_comments.author_id TEXT`。当 `subject_type='user'` 时，这里存的是**用户的整数 id 转 TEXT**，与 §7「users 用整数 user_id」的豁免约定相悖，也与 `owner_user_id INTEGER` 不一致。建议 member 表对 user 成员单列 `user_id INTEGER`，或统一文档化该混用。
2. **软外键过多**：`project_tasks.parent_id/thread_id/origin_node_id`、`project_comments.task_id/thread_id`、`artifacts.task_id`、`timeline_events.task_id`、`node_mark_logs.comment_id` 均未声明 `REFERENCES`。可接受（避免破坏 threads 表），但应在 Repo 层补存在性校验，否则会静默产生孤儿引用。

### #4 PG 版差异（IDENTITY / BIGINT）—— 部分成立

- `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` ✅ 与仓库一致（`001_initial.pg.sql:11`、`014_user_policy.pg.sql:8`、`007_*.pg.sql:21`）。
- **「时间戳列用 BIGINT」不成立为通用约定**：`001_initial.pg.sql` 中 users/agents/providers 等的 `created_at/updated_at` 全是 `INTEGER NOT NULL`（如 `001_initial.pg.sql:18`）；`knowledge_bases` 用 `INTEGER`（`007_*.pg.sql:82-83`）；`user_policies` 用 `INTEGER`（`014_*.pg.sql:14-15`）。只有 `published_experts`（`007_*.pg.sql:53-54`）、`trajectory_events`/`thread_messages`/`user_sso_identities`（migrate.py helpers）用 BIGINT。仓库本身不一致，计划把它当「仓库统一写法」是误判。
- 附带提醒：仓库里 `user_id` 外键有 `INTEGER`（001/007）也有 `BIGINT`（014:10、user_sso_identities）两种，`owner_user_id INTEGER REFERENCES users(id)` 与 001 一致、可行，但应保持与同库新表风格统一。

### #6 迁移框架约束 —— 部分成立（缺 v18 幂等 helper）

- `_discover` 重复版本号 `RuntimeError`（`migrate.py:57`）：018 空缺，无碍。
- `_split_pg_sql` 按 `;\s*\n` 切分（`migrate.py:20,23`）：计划 DDL 无「字符串内分号+换行」，安全；行尾 `-- 注释` 会随语句保留，PG 可接受。
- **真正的缺口**：`_apply_sqlite_migration` 对 2–17 每个版本都有幂等 `_ensure_*` 分支（`migrate.py:1592-1705`），v18 会落到 `conn.executescript(sql)` 兜底（`migrate.py:1706-1708`）。计划 DDL 用裸 `CREATE TABLE`（无 `IF NOT EXISTS`）且未提供 v18 的 `_ensure_projects_schema` helper。`run_migrations` 连跑两次不报错（靠 watermark）成立，但**「版本被跳过 / 高水位被 clamp」时的修复路径缺失**（v2–v17 都有）。建议：v18 也配套幂等 helper，或在 DDL 用 `CREATE TABLE IF NOT EXISTS`。

### #12 Owner 闸门复用 HITL —— **不成立（重点，语义不匹配）**

`HitlPolicy`（`octop-harness/src/octop_harness/security/models.py:46-52`）docstring 明写「Human-in-the-loop approval **before selected tools execute**」。全链路是**工具调用审批**：

- `SecurityPolicy.resolve_interrupt_on()` 把 HITL 映射为 `{tool_name: {allowed_decisions: [approve|edit|reject|respond]}}`（`models.py:248-295`）；
- `agent.py:1369` `_resolve_interrupt_on()` 只对**模型将要调用的工具**生效；
- `resume_hitl()`（`agent.py:529`）恢复的是**被暂停的那次工具调用**；
- `hitl/coordinator.py` 的记录按 `thread_id/agent_id/user_id/session_key` 组织，`action_requests` 是工具审批卡，`/approve` `/reject` slash 是对工具卡做决定。

而「Owner 确认需求节点草案」是**业务审批**：没有工具调用边界、可异步跨 turn 发生、决策对象是一份文档而非一次工具执行。把 HITL 拉来承载它，需要把「确认节点」伪造成一个自定义工具并让模型在正确时点调用——计划没有这层设计，因此「复用 HITL 不另造审批流」**不成立**。

**更好的复用对象是现成的 `ask_user_question`**（计划完全没提）：
- 内置工具 `octop_harness/builtin/tools/ask_user.py`，默认挂载（`agent.py:1347`），中断配置 `allowed_decisions=["respond"]`（`agent.py:1380`），官方定位「a collaboration channel, not an approval gate」（`agent.py:1360-1364`）；
- IM 卡片 `format_ask_card`（`hitl/format.py:129`）+ 答案收集 `collect_ask_reply`（`hitl/coordinator.py:230`）已就绪。

建议：Owner 拍板走 `ask_user_question`（或在此基础上加「确认/驳回」决策类型），而非扭曲 HITL。

### #13 讨论线复用 thread_messages —— 部分成立

`threads` 表是**单 agent**：`agent_id TEXT NOT NULL`（`001_initial.sql:136`）。`thread_messages` 按 `thread_id` 归属一个 agent 的对话流。一个「任务讨论线」若包含 Leader + 专家 + Owner + 真人等多参加者，**无法塞进同一条 thread_messages 流**（每个专家/团队各有自己的 thread）。计划自己用 `project_comments` 兜底结构化评论（方向正确），但「讨论线复用 thread_messages」的表述掩盖了「多参加者讨论必须落在 project_comments + 多个 thread（project_rooms）」这一事实，应显式写明，避免实现时误以为一条 thread 能装下整条讨论线。

### #15 产物复用上游 thread_artifacts —— 部分成立（命名冲突）

复用本身可行：`threads.artifacts` 列存在（`007_*.sql:16`、migrate.py:1443），`thread_artifacts_payload()`（`infra/agents/thread_artifact.py:183`）返回 `{artifacts, artifact_refs}`，`ThreadRepo.append_artifacts`（`infra/db/repos/threads.py:293`），`ThreadArtifactsMiddleware` 自动写路径。

**但计划附录 A 又新建了一张同名 `artifacts` 表**（project_id/task_id/kind/uri/commit_ref/version/hash，计划第 721-737 行）。于是出现两个「artifacts」：上游 `threads.artifacts` 列（thread 级文件路径）与自建 `artifacts` 表（项目级产物登记）。计划未说明二者关系，存在命名混淆与重复登记风险。建议：自建表改名（如 `project_artifacts`），并明确它引用 `threads.artifacts` 的路径而非重新扫描。

### #18 计划 `文件:行号` 引用抽查 —— 部分成立（2 处错误，其余准确）

抽查 17 处，15 处准确/基本准确（`memory_client.py:90`、`memory_portable.py:47`、`teams/service.py:24`、`util.py:16`、`permissions.py:50`、`app.py:203`、`openapi_meta.py:57`、`errors.py:13/133`、`services.py:37/66/97`、`test_acl_gate_coverage.py:12`、`layoutModeStorage.ts:18`、`useSessions.ts:34`、`threads.py:213`、`history.py:99`、`agent.py:529/1369`）。两处错误：

1. **`team_manager.py:534`**（计划第 246 行，Octop 侧 `infra/agents/teams/team_manager.py`）：该行是 `install_host_dispatch` 的 docstring「Force team hosts onto inbox dispatch and room streaming」，**不是 `peer_invoke_mode`**。`peer_invoke_mode`/sync 降级在 `team_manager.py:571-574`（「Async ask_agent is a group room; sync is a 1:1 tool return … hosts cannot sync-dispatch」）以及 harness `team_manager.py:149-169/203-208`。
2. **「CHANGELOG 说 1–200」**（计划第 523 行）：实际 `GET /agents/{agent_id}/threads` 的 `limit: int = 50`（`history.py:102`），无 clamp。数字写错（方向「未见 clamp」是对的）。

## 四、计划未发现的可复用机制

1. **`ask_user_question` 工具链**（`octop_harness/builtin/tools/ask_user.py`、`agent.py:1347/1380`、`hitl/format.py:129`、`hitl/coordinator.py:230`）——Owner 确认/需求澄清的更佳载体，替代 HITL 扭曲（见 #12）。
2. **`trajectory_events`**（migrate.py:1006 起，`TrajectoryEventRepo`）——与计划 `timeline_events` 同类的追加式事件账本，可参考其 `(thread_id, seq)` 结构，避免另起炉灶。
3. **`audit_log`**（`001_initial.sql:231`，`AuditRepo`）——通用留痕表，`node_mark_logs`/`timeline_events` 的留痕需求可对齐其 actor/action/target/payload 形状。
4. **`room~member` 房间线程命名 + room wall 投影**（`thread_artifacts.py:34` `peer_room_thread_id`、`infra/agents/teams/team_manager.py` 的 `stream_peer_to_room`/`_push_room_snapshot`）——`project_rooms` 的「群聊房间」可直接挂靠既有房间投影，只补 `project_id` 关联。
5. **`ThreadRepo.append_artifacts` + `peer_room_thread_id`**——团队房间产物会同时镜像到 room 线程（`thread_artifacts.py:120-122`），项目产物回链可复用该「member→room」镜像，无需重复扫描。

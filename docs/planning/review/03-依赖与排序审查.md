## 二、未声明依赖清单（8 条）

### D1（blocker）— 项目 KB 创建/绑定任务缺失，T3.4 无法落地
`projects.kb_id`（附录 A DDL）为 `TEXT` 可空。`POST /api/projects`（S2 接口契约）只写 owner 成员行 + 分配 `memory_namespace`，**不创建 KB、不写 kb_id**。计划没有任何任务卡负责「创建项目 KB 并回写 `projects.kb_id`」。
源码核实：KB 创建走 `POST /api/knowledge-bases`（`api/routers/knowledge_bases.py:531`），写文档走 `POST /api/knowledge-bases/{kb_id}/documents/text`（`:688`），且需要 `require_permission("knowledge_bases")` + `assert_knowledge_usable`。T3.4 直接「写项目 KB(kb_id)」在 kb_id 为 NULL 时必失败，AC-10 无法验收。
**建议**：新增任务卡「项目 KB 生命周期」（立项时自动建 KB + 绑定 kb_id + 归档处理），或明确并入 T2.1，并在附录 C 补产出。

### D2（blocker）— 迁移 018 建 10 张表，但 repo 层只覆盖 3 张
T1.3 只定义 `ProjectRepo / ProjectMemberRepo / ProjectTaskRepo`。其余 7 张表（`project_comments` / `node_mark_logs` / `requirement_nodes` / `project_rooms` / `project_room_members` / `artifacts` / `timeline_events`）**没有任何 repo 任务**，而 T2.3、T3.1–T3.5 都要读写它们。
**建议**：在 T1.3 或新增「T3.x 各表 repo」任务中把 10 张表的 repo 全部列全（可拆到 T3 各卡，但必须显式出现）。

### D3（blocker）— 迁移号断言实际约 16 处 / 8 文件，计划只改 7 处 / 1 文件
计划铁律 3 与 T1.2 声称「7 处 `assert v == 17 → == 18`，只改 `tests/unit/db/test_db_pool.py`」。实测（grep 全仓）：
- `test_db_pool.py` 内：`assert v == 17` **2 处** + `assert version == 17` **5 处** = 7（本文件成立）；
- **其余 7 个测试文件共 9 处**也会因 bump 到 18 而 fail：`test_skill_package_icons.py`(2)、`test_skill_packages_repo.py`(1)、`test_repo_knowledge.py`(1)、`test_published_experts_repo.py`(1)、`test_clip_thread_title.py`(1)、`test_agent_profile_columns.py`(1)、`test_system_archive.py`(2)。
- §7 检测脚本 `sed "s/assert v == ${MINE#0}/..."` 只匹配 `assert v ==`，**漏掉 5 处 `assert version ==`**，也漏掉其余 7 个文件。
**建议**：T1.2 改为「全仓 grep `== 17` 同步改」，脚本改为 `grep -rn "== 17" tests/` 逐处替换；否则 `make all` 必红。

### D4（high）— T3.3 Owner 闸门依赖 HITL 接线，计划未说明启用/触发
HITL 不是「复用即免费」：需要 agent 配置里有 `interrupt_on`（`octop-harness/config/__init__.py:724`）或 thread 级 `hitl_policy`（`infra/db/repos/threads.py` / `security/hitl_session.py`），并定义「`pending_confirm` 节点 → 触发哪个 HITL 中断 → Owner 在 IM/群里拍板 → `resume_hitl`」的完整接线。计划 §S2.5 只列了复用点（HitlPolicy / interrupt_on / resume_hitl / coordinator），没有任务负责配置或注册。
**建议**：T3.3 增加前置/产出：「为 Owner 闸门注册/启用 HITL 策略 + 定义触发条件」，并明确它是否要改 harness 配置（若改 harness 则与「M1 不碰 harness」的声明冲突，需澄清）。

### D5（high）— T2.5 派单未指明具体端点
计划只写「建/复用 thread + 首条消息 + 团队 room 机制」，未指明：
- 建 thread：`POST /api/agents/{agent_id}/threads`（`chat/history.py:213`）或 `infra/gateway/threads.py:427 ThreadManager.create_thread`；
- 发消息：dashboard 走 WebSocket `/agents/{agent_id}/chat/ws`（`chat/ws.py:32`）或 gateway processor，**没有简单 REST「发消息」端点**；对非 team assignee（纯 agent）的服务端发送路径计划未定义。
**建议**：T2.5 写明内部调用链（ThreadManager.create_thread + 服务端 stream 或 `bind_peer_session`/`ask_agent` 触发点），并区分「派给 agent」与「派给 team」两条路径。

### D6（medium）— T2.6 依赖 S0 但 S0 被定义为「可并行/后置」
T2.6 已声明「依赖 S0」，但 §3 说 S0「与 S1/S2 无依赖，可并行或 M1 后补」。若按此并行/后置执行，S2 内的 T2.6 会阻塞在 S0 未完成上。风险未被登记进 §8 风险登记册，也无排序闭环（如「T2.6 移到 S0 完成后」）。
**建议**：把「T2.6 排在 S0 之后」或「S0 与 S1 并行但必须在 S2 收口前完成」写入里程碑约束。

### D7（medium）— T2.1 与 T1.4 产出同一文件，边界未定义
T1.4 产出「`projects/service.py` + `api/routers/projects.py`（骨架）」；T2.1 产出同为「`projects/service.py`、`api/routers/projects.py`（CRUD）」。两者是同一文件先后两次写，且未定义「骨架」与「完整 CRUD」的分界。这既是依赖也是写冲突（W1）。

### D8（medium）— T2.5 间接触及 `infra/agents/teams`，上游重构签名风险未登记
T2.5 复用 team room / `ask_agent`（`infra/agents/teams/team_manager.py`、`service.py`）。它不**改**这些文件，但**依赖其公开接口**（TeamRoomManager / ask_agent 触发）。`infra/agents` 正被上游重构（09-25 `refactor(infra): group agents modules`），接口签名可能变动 → T2.5 是 M1 内唯一间接触及 `infra/agents` 的任务，该风险未在风险登记册单独列出。
**建议**：T2.5 对 team room 的调用封装在一个 `infra/projects` 内的小门面里，隔离上游接口变动。

## 五、M1 可独立交付性判定

**结论：否（相对 M2 独立，但 M1 内部不完整，不能按宣称范围独立交付）。**

- **相对 M2 是独立的**：M1（S1+S2+S2.5，S0 并行）不依赖 S3（项目记忆）、S4（跨用户）、S5（commit 回写）——这三块正确推迟，且不编辑 `infra/agents`。判定这部分成立。
- **但 M1 内部存在 2 个 blocker 缺口，阻断其宣称的「Owner 拍板 + 产出归档」闭环**：
  1. **D1**：无任务创建/绑定项目 KB（`projects.kb_id`），T3.4 与 AC-10 无法验收；
  2. **D2**：10 张表中 7 张无 repo 任务，T2.3 / T3.1–T3.5 的实现无 repo 可用。
- 另有 2 个 high 缺口（D4 HITL 接线、D5 派单端点）会使 T3.3 / T2.5 的验收标准无法用当前任务卡落地。

**修复前提**：补「项目 KB 生命周期」任务 + 「7 张表 repo」任务（或并入 T1.3/T3 各卡显式声明产出）后，M1 即可独立交付。
